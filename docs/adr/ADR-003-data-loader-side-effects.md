# ADR-003: data_loader Import-Time Side Effect

**Status:** Proposed
**Date:** 2026-05-17

## Context

`data_loader.py` executes `np.load()` at module level on line 13:

```python
stats = np.load(str(config.norm_stats_path), allow_pickle=True).item()
```

This runs when Python processes `import slitless.data_loader` or any transitive import (e.g., `from slitless.recon import scipy_solver` triggers it because `recon.py` line 11 does `from slitless.data_loader import meas_transform as unet_meas_transform, param_inv_transform`).

**Consequences:**

1. If `norm_stats.npy` is missing (fresh install, wrong machine, data not yet generated), **the entire package is unimportable**. `from slitless.recon import ...` raises `FileNotFoundError`.
2. The `stats` variable is a module-level global used by four transform functions (`meas_transform`, `meas_inv_transform`, `param_transform`, `param_inv_transform`). These functions default the `stats` parameter to the module global, effectively coupling all consumers to the module state.
3. The hardcoded `6000` value in `meas_transform` (line 18: `return meas/6000`) ignores `config.intensity_scale = 6000.0`. If either value changes, they must be updated in two places.

The `norm_stats.npy` file is generated by `scripts/generate_dset_v5.py` (line 10: `STATS_OUT_PATH`). A new user or fresh environment would need to run this script *before* importing the library — a hidden dependency.

## Decision Options

### Option A: Status Quo
**Description:** `np.load()` at module level. Import fails if file missing. Hardcoded `6000` in `meas_transform`.

**Pros:**
- Works correctly for the sole developer (who has the file).
- No code changes needed.

**Cons:**
- Package import blocked for anyone without the specific data file.
- Hardcoded `6000` is a maintenance trap — diverges from `config.intensity_scale`.
- Transitive imports are a landmine: doing `from slitless.recon import scipy_solver` requires the stats file to exist, even though scipy_solver doesn't use it.
- Cannot run `help(slitless.recon)` or `import slitless.recon` in a CI environment.

### Option B: Lazy Loading via Factory Functions (Recommended)
**Description:** Transform functions become factory functions that defer stats loading to first call, not import time.

```python
# data_loader.py

_stats_cache = None

def _get_stats():
    global _stats_cache
    if _stats_cache is None:
        _stats_cache = np.load(str(config.norm_stats_path), allow_pickle=True).item()
    return _stats_cache

def meas_transform(meas, stats=None):
    if stats is None:
        stats = _get_stats()
    return meas / config.intensity_scale  # Use config value, not hardcoded 6000

def param_transform(params, stats=None):
    if stats is None:
        stats = _get_stats()
    params[0] /= config.intensity_scale
    params[1] = (params[1] - stats['vel_mean']) / stats['vel_std']
    params[2] = (params[2] - stats['width_mean']) / stats['width_std']
    return params

def param_inv_transform(params, w_kms=False, stats=None):
    if stats is None:
        stats = _get_stats()
    params[...,0,:,:] *= config.intensity_scale
    params[...,1,:,:] = stats['vel_std'] * params[...,1,:,:] + stats['vel_mean']
    params[...,2,:,:] = stats['width_std'] * params[...,2,:,:] + stats['width_mean']
    if w_kms:
        params[...,2,:,:] *= SPEEDOFLIGHT / WAVELENGTH
    return params
```

`BasicDataset` and `OntheflyDataset` classes are unaffected — they only import `add_noise` and `forward_op`, not the stats.

**Pros:**
- `from slitless.recon import scipy_solver` works without the data file — unblocks CI, fresh installs, and documentation tools.
- `config.intensity_scale` is now the single source of truth for scaling, eliminating the hardcoded `6000`.
- All existing call sites work unchanged — they don't pass `stats` and get the lazy-loaded value.
- Module-level global `stats` removed — no hidden import-time side effects.
- Minimal code change: ~15 lines added, ~5 lines changed.

**Cons:**
- First call to any transform function incurs a one-time ~10-50ms `np.load` cost (negligible in practice).
- Thread safety: `_get_stats()` is not thread-safe under contention. For a single-developer codebase with no threading in data loading, this is acceptable. If needed later, add `threading.Lock`.
- The `stats` parameter default changes from module global to factory — existing code that explicitly passes `stats=stats` will need updating (only internal call sites affected).

### Option C: Explicit `init()` Function
**Description:** Add an `init_norm_stats()` function. Users call it before using transforms. Import-time no longer loads the file.

**Pros:**
- Explicit dependency — clear what data is needed and when.
- Import semantics are clean.

**Cons:**
- **Creates ongoing friction.** The developer must remember to call `init_norm_stats()` before running any script. If forgotten, transforms crash at runtime with a confusing error about `stats` being `None`.
- All 21 scripts and any ad-hoc `python -c` experiments need a boilerplate line added.
- Violates developer familiarity rule 4 (ongoing friction without gain).

### Option D: Remove Normalize Transforms Entirely
**Description:** Delete `meas_transform`, `meas_inv_transform`, `param_transform`, `param_inv_transform`. Normalization becomes the caller's responsibility.

**Pros:**
- Eliminates the stats dependency entirely.
- Simplest possible code.

**Cons:**
- **Massive disruption.** These functions are imported and called in:
  - `recon.py` (line 11, used in `Reconstructor.meas_transform()` and `recon_inv_transform()`)
  - `train.py` (likely used as DataLoader transforms)
  - `evaluate.py` (likely used in prediction pipeline)
  - Multiple scripts
- Violates developer familiarity rule 1 — all existing code must be rewritten to do stats loading and scaling inline.
- Not practical for a single-developer codebase without a compelling reason.

## Developer Familiarity Impact

| Question | Option A | Option B | Option C | Option D |
|---|---|---|---|---|
| `from slitless.recon import X` works without stats file? | No (crashes) | Yes | Yes (but transforms crash at runtime) | Yes |
| `from slitless.data_loader import BasicDataset` works? | No | Yes | Yes | Yes |
| Existing call sites change? | No | No (backward compat) | Must add `init()` call | Must rewrite all |
| `meas_transform` still uses 6000? | Yes (hardcoded) | No (uses config) | Depends | N/A |
| Migration cost | None | ~15 lines changed | Add init to 21 scripts | Very high |

## Recommendation

**Option B** (lazy loading with factory functions). It fixes the import-blocking bug, wires `config.intensity_scale` to its consumer, and requires zero changes to existing call sites. The one-time `np.load` cost on first transform call is negligible compared to the existing `import slitless` cost.

Additionally, remove the unused `meas_inv_transform` function if it is truly dead code (no callers found in the codebase) to reduce the surface area.

**Implementation note:** The existing line 13 `stats = np.load(...)` and its module-level global must be deleted, not just commented out. If not deleted, `import slitless.data_loader` will still crash when the file is missing. The `_get_stats()` function is the only path to loading stats.
